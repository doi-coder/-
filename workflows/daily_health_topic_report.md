# Workflow: 매일 건강 콘텐츠 트렌드 리포트

> 🎯 **북극성 목표 (모든 판단의 기준, 2026-08-10 사장님 확정)**: 이 워크플로우의 모든 선택 —
> 카테고리 로테이션, 제목, 검색의도 분석, 초안 문체 — 은 전부 하나의 목표를 위해 존재한다:
> **블로그 검색 유입을 극대화해서 하루 애드포스트 수익을 점차 늘리는 것.** 구체적으로 네
> 가지 기준으로 판단한다: (1) 그날그날 검색량이 높은 관련 키워드를 고르되, 어제·그제와
> 겹치지 않는 소재로 매일 다른 검색 니즈를 반영한다. (2) 제목은 어그로가 아니라 본문 내용과
> 정확히 일치해야 하고, 거짓·과장 정보를 지어내지 않는다. (3) 초안 하나하나가 실제 검색
> 유입으로 이어지도록 쓴다. (4) 이 모든 게 쌓여서 하루 애드포스트 수익을 점차 늘리는 게
> 최종 목표다. 정보가 정확하고 유용한 것만으로는 부족하다 — 실제로 사람들이 검색해서
> 들어오고, 다시 찾아오게 만드는 게 최우선이다. [[economy_daily_reports]], [[stock_deepdive_blog]]도
> 같은 목표를 공유한다.

## ⚠ 반드시 지킬 것 — 지어내지 않기 (건강 정보 버전)
제목·검색의도 분석·초안은 실시간 검색 트렌드 데이터를 근거로 하지만, 실제 문장은 에이전트가
직접 쓴다. 의료 정보를 다루므로 다음을 반드시 지킨다:
- 확신 없는 의학적 주장(정확한 유병률 수치, 특정 치료 효과 단정 등)을 지어내지 않는다.
  일반적으로 널리 알려진 상식 수준의 정보만 쓰고, 구체적 수치가 필요한데 확신이 없으면
  숫자 없이 정성적으로("많은 사람들이 겪는", "흔히 나타나는" 등) 서술한다.
- "당신은 OO입니다" 처럼 진단하듯 단정하지 않는다. "이런 증상이 있다면 OO일 수 있어요, 병원
  상담을 권해요"처럼 정보성 톤을 유지한다.
- 특정 약물·시술·제품(브랜드명 포함)을 추천하는 어조를 쓰지 않는다 — 의료광고법/약사법에
  저촉될 수 있다.
- 초안 끝에는 항상 "이 글은 정보 제공 목적이며 진단·치료를 대신하지 않습니다. 증상이 있다면
  병원 상담을 권합니다" 같은 문구를 짧게 남긴다.

## ⚠ 네이버 검색 데이터 취급 원칙 (2026-11-01 사장님 확정)
네이버는 2026-09-07부터 검색 API 약관을 개정해 **검색 결과를 AI에 입력하거나 요약·가공에 쓰는
것을 금지**했다(언론 보도·분석 기준. 허용되는 건 출처·원문 링크와 함께 가공 없이 보여주는 것).
그래서 이 리포트는 데이터를 두 갈래로 나눈다:
- **AI(에이전트)가 읽는 것** — `.tmp/health_data/candidates_<날짜>.json`: 데이터랩 검색어
  트렌드, 검색광고 연관키워드(월간 검색량·광고 경쟁도), 유튜브, 발행 글 목록, 업무 지식 체크리스트.
- **사람만 보는 것** — `.tmp/health_data/display_<날짜>.json`: 네이버 검색 API 결과(블로그 글 수,
  지식iN 질문). `tools/report_builder.py`가 PDF를 만들 때 직접 읽어 출처와 함께 그대로 표시한다.
- **에이전트는 `display_<날짜>.json`을 열거나 읽지 않는다.** `tools/naver_blog_search.py`,
  `tools/naver_kin_search.py`를 직접 실행하지도 않는다. 블로그 글 수가 궁금해도 추측하지 않고
  비워둔다 — PDF에 자동으로 표시된다.
- 데이터랩(검색어 트렌드)과 검색광고 API가 이 금지 조항에 해당하는지는 아직 확정되지 않았다.
  네이버 약관 원문이나 문의 결과로 해당한다고 확인되면 같은 방식으로 표시 전용으로 옮긴다.

## 실행 방법 (Agent가 할 일)
1. `.env` 파일에 아래 값이 다 채워져 있는지 확인한다 (`.env.example` 참고).
   - `NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET`
   - `YOUTUBE_API_KEY`
   - 하나라도 비어 있으면 실행하지 말고, 어떤 값이 빠졌는지 사장님께 알려준다.
2. `python tools/run_daily_report.py` 한 번 실행한다 (데이터 수집 전용 — PDF는 아직 안 만듦).
   - 내부적으로 하는 일: 데이터랩 검색어트렌드 조회 → 오늘 날짜 로테이션으로 카테고리 2개
     배정(카테고리 안의 구체적 키워드도 날짜별로 로테이션) → 검색광고 롱테일 후보 → 관련
     키워드로 유튜브 인기 영상 조회 → AI용 후보 JSON 저장. 네이버 검색 결과(블로그 글 수,
     지식iN 질문)는 표시 전용 display JSON에 따로 저장한다 (위 "네이버 검색 데이터 취급 원칙").
3. `.tmp/logs/YYYY-MM-DD.log`를 읽는다. `CANDIDATES_READY: <경로>` 줄이 있으면 그 JSON을
   읽어서 다음 단계로 넘어간다. 실패했으면 "실패했을 때 대응 원칙" 참고.
3-1. `data/published_posts.md`를 처음부터 끝까지 읽는다 (아래 "중복 방지" 참고).
4. **JSON의 `candidates` 각 항목(오늘 3개)마다 아래를 직접 작성한다.** 먼저 `longtail_options`가
   있으면 아래 "롱테일 키워드 선택" 기준으로 메인 키워드를 정한다. (아래 "제목·키워드
   선정 기준", "블로그 초안 작성 지침" 참고):
   - `search_intent`: 이 키워드를 검색하는 사람들이 실제로 뭘 원해서 검색했을지
   - `title`: 그 검색 의도에 가장 잘 맞는 네이버 블로그 제목 1개
   - `target_analysis`: 타겟 독자 분석 (연령·성별·상황을 구체적으로 — candidate의 segment
     데이터를 참고하되 그대로 베끼지 말고 왜 그런지 풀어쓴다)
   - `keyword_analysis`: 메인 키워드 분석 (candidate의 rising_pct와 롱테일의 월간 검색량을 근거로 왜
     이 키워드가 지금 다룰 만한지)
   - `differentiation`: 이미 발행한 글 중 관련 글이 있으면 그 제목과, 이번 글이 어떤 다른
     각도인지 한 문장. 관련 글이 없으면 "관련 기존 글 없음".
   - 800~1200자 포스팅 초안을 작성해서 `.tmp/reports/health_report_<날짜>_draft1.txt`,
     `_draft2.txt`, `_draft3.txt`로 각각 저장한다 (순서는 candidates 순서대로). 파일 맨 위에
     `search_intent`/`target_analysis`/`keyword_analysis`를 요약한 분석 블록을 먼저 적고,
     **`=== 본문 ===` 한 줄을 넣은 뒤** 그 아래에 실제 초안을 쓴다 (검증 도구가 이 줄 아래만
     초안으로 보고 검사한다. 이 줄이 없으면 검증 실패).
4-1. **수술실 업무 주제 3개를 정한다** (아래 "수술실 주제 추천 지침" 참고). 각 항목은
   `title`, `keyword`, `axis`, `source`, `source_detail`, `target`, `outline`, `differentiation`.
   블로그 글 수는 채우지 않는다 — PDF를 만들 때 자동으로 표시된다.
5. 위에서 채운 내용으로 `posts` 배열을 만들어 `candidates`를 대체하고, 수술실 주제는
   `or_topics` 배열로 추가한다 (다른 필드 `or_axes`/`segment_trends`/`youtube_top`/
   `blog_saturation`/`failed_sources`/`report_date`는 그대로 유지),
   `.tmp/health_data/report_<날짜>.json`로 저장한다.
5-1. **완료 전 검증을 돌린다** (아래 "완료 전 검증" 섹션). `python tools/draft_checker.py
   .tmp/health_data/report_<날짜>.json` → 실패 항목을 고치고 다시 돌린다. 이 단계를 통과하기
   전에는 PDF를 만들거나 사장님께 아무것도 보내지 않는다.
6. `python tools/report_builder.py <5번 json경로> .tmp/reports/health_report_<날짜>.pdf`를
   실행한다 (python이 없으면 python3).
7. 생성된 PDF와 초안 txt 파일 **넷 다**(PDF 1개 + 건강 초안 txt 3개) 채팅 응답에 **직접 첨부**해서
   전달하고, 푸시 알림도 보낸다.
8. 결과를 사장님께 보고한다:
   - 성공: 건강 제목 3개 + 수술실 제목 3개를 짧게 요약하고 PDF·초안 3개를 첨부.
   - 모든 보고 끝에 **검증 결과 요약**을 붙인다: "검증 47개 중 통과 45 · 확인필요 2" 한 줄과,
     실패·확인필요였던 항목마다 한 줄(무엇이었고 어떻게 처리했는지).
   - 일부 실패(예: 유튜브 쿼터 초과로 이전 데이터 사용): 무슨 일이 있었는지 쉬운 말로 알려주고,
     PDF는 그래도 전달한다 (PDF에도 "갱신 실패" 표시가 남음).
   - 전체 실패(PDF 자체가 안 만들어짐): 에러 내용을 쉬운 말로 설명.

## 롱테일 키워드 선택 (검색광고 API, 2026-11-01 추가)
- 배경: 미리 정해둔 약 60개 키워드만 돌리면 결국 주제가 고갈된다. 그래서 각 후보의 씨앗 키워드로
  네이버 검색광고 '연관키워드'를 받아 `longtail_options`에 넣는다 (`tools/naver_searchad.py`).
  각 항목: `keyword`, `monthly_total`(월간 검색량 PC+모바일), `monthly_pc`, `monthly_mobile`,
  `competition`(광고 경쟁: 낮음/중간/높음). 월간 검색량 큰 순으로 정렬돼 있다.
  블로그 글 수는 네이버 검색 데이터라 여기 없다 — PDF에만 표시된다.
- **`longtail_options`가 있으면 메인 키워드는 이 목록에서 고른다.** 기준 순서:
  1. 건강 정보 글로 쓸 수 있는 키워드일 것 — 브랜드·제품명, 쇼핑·가격 키워드(예: "OO 추천",
     "OO 최저가")는 제외 (의료광고법/약사법, "특정 제품 추천 금지" 원칙).
  2. `data/published_posts.md`의 기존 글과 같은 각도가 아닐 것 (중복 방지 규칙 그대로).
  3. 씨앗 키워드 그대로(예: "루테인")보다 의도가 구체적인 롱테일(예: "루테인 부작용",
     "장염 빨리 낫는 법")을 우선한다. 구체적일수록 경쟁이 덜하고 제목·본문이 검색 의도에 맞기 쉽다.
  4. 그중 월간 검색량이 충분한 것(대략 1,000 이상). 광고 경쟁이 '낮음/중간'이면 가산점.
- 고른 키워드를 `posts[].keyword`로 쓰고, 원래 씨앗 키워드는 `seed_keyword`로 남긴다.
  `keyword_analysis`에는 월간 검색량과 광고 경쟁도를 실제 값 그대로 적는다.
- `longtail_options`가 비어 있으면(키 미설정 또는 호출 실패) 기존처럼 배정된 키워드를 쓴다.

## 제목·키워드 선정 기준
제목·키워드는 방문자 수를 결정하는 가장 직접적인 지점이다 — 내용이 아무리 좋아도 검색에서
안 걸리면 방문자로 이어지지 않는다(북극성 목표 참고).
- `candidates`의 `reason`(데이터랩 상승률)과 롱테일 월간 검색량을 `keyword_analysis`의 근거로 활용한다
  — 새로 조사할 필요 없이 `tools/run_daily_report.py`가 이미 계산해둔 데이터다.
- 검색 의도는 크게 두 갈래로 나눠서 생각한다: "이게 뭔지/내 얘기인지 확인하고 싶다"(개념·자가진단형)
  와 "지금 뭘 해야 하는지 알고 싶다"(관리법·실천형). 이 키워드가 둘 중 어느 쪽에 가까운지
  판단해서 제목에 반영한다 (예: "OO 자가진단", "OO 관리법", "OO 뜻").
- 제목은 막연하게 짓지 않는다 — `search_intent`에서 정리한 의도가 제목만 보고도 짐작될 정도로
  구체적이어야 한다.

## 중복 방지 (2026-11-01 사장님 확정)
- 기준 파일: `data/published_posts.md` (발행일 | 조회수 | 제목). 건강·수술실 둘 다 적용.
- **이미 쓴 주제를 같은 각도로 다시 추천하지 않는다.** 예: "탈모초기증상, 하루 몇 개 빠지면
  위험할까"가 있으니 같은 자가진단형 탈모 글은 안 됨.
- **같은 주제라도 다른 방향이면 추천해도 된다.** 다른 대상 독자(간호사 ↔ 환자), 다른 질문
  형태(뜻 → 비교 → 오해 반박 → 후속편), 다른 비교 축이면 OK. 이때 `differentiation`에 관련
  기존 글 제목과 무엇이 다른지 적고, 기존 글은 내부링크 후보로 안내한다.
- 건강 키워드는 데이터로 배정된 것이라 바꾸지 않는다 — 이미 쓴 키워드가 배정되면 키워드는
  유지하고 각도를 바꾼다.
- 2024년 경제 글은 현재 방향과 무관하므로 중복 판단에서 무시해도 된다.
- 사장님이 새 글을 발행하면 이 파일 맨 위(해당 연도 섹션)에 한 줄씩 추가하고, 수술실 글이면
  `data/or_knowledge_map.md`의 해당 항목도 ✅로 바꾼다.

## 수술실 주제 추천 지침
- 블로그 컨셉: 현직 수술실(스크럽) 간호사 '도이'가 신규 수술실 간호사·간호학생, 그리고 수술을
  앞둔 일반인에게 설명하는 블로그.
- 사장님은 성형외과를 제외한 거의 모든 과 수술에 들어간다. 성형외과는 수술 자체가 아니라
  운영·시스템 각도로만 다룬다.
- **3개 주제를 이렇게 고른다** (2026-11-01 확정). 머릿속 지식만으로 즉흥적으로 떠올리지 않기 위함이다.
  각 주제의 `source`/`source_detail`에 출처를 적는다.
  1·2. `"업무 지식 체크리스트 빈칸"` 2개 — `data/or_knowledge_map.md`에서 ⬜(아직 안 씀) 또는
     🔶(일부만) 항목을 **서로 다른 영역에서** 하나씩. `source_detail`에는 영역과 항목명.
     M(환자 질문형) 영역은 조회수가 잘 나오는 유형이니 자주 포함한다.
  3. `"오늘의 주제 축"` 1개 — JSON의 `or_axes` 중 1·2번과 겹치지 않는 축에서. `source_detail`에는 축 이름.
- 지식iN 질문은 **에이전트가 보지 않는다**(네이버 검색 데이터). PDF 맨 뒤에 "직접 훑어보기" 목록으로
  붙어서 사장님이 직접 글감을 고른다.
- `axis`에는 그 주제가 속하는 `or_axes` 축 이름을 적는다 (축과 무관하면 가장 가까운 분류).
- 발행 글 조회수에서 확인된 강한 유형을 우선 참고한다:
  (1) 기구·수술 방식 비교형 — IM nail 기구, hip bipolar vs THR, femur nail 기구 등이 4천~5천대
  (2) 환자 질문에 수술실 간호사가 답하는 형 — 복강경 후 어깨 통증, 수술 탈의, 수술 전 금식 등
  (3) 신규 간호사 실무형 — 스크럽/써큐 차이, 봉합사·니들 종류, 첫 출근 준비물
- 제목에는 수술실 현장에서 실제로 부르는 용어(영문 약어 포함)를 쓴다. 예: '골수정'보다
  'IM nail', 'antegrade'보다 'humerus head 쪽'처럼 현장 용어를 우선하고 필요하면 병기한다.
- `outline`은 3~5단계 흐름으로 짧게. `target`은 신규 간호사/간호학생/환자 중 누구인지 명확히.
- 수술실 주제는 데이터랩 검색량이 잘 안 잡히므로 상승률이나 검색량을 지어내지 않는다.

## 블로그 초안 작성 지침
초안의 역할은 정보 전달이 아니라 "검색해서 들어온 사람이 끝까지 읽고, 다음에도 이 블로그를
찾아오게 만드는 것"이다(북극성 목표 참고) — 그래서 도입부 후킹과 키워드 배치가 특히 중요하다.
- **분량**: 800~1200자 내외.
- **어조**: 신문기사체·의학논문체가 아니라 자연스러운 1인칭 블로그 말투("~해요", "~인데요").
  `target_analysis`에서 정한 독자가 편하게 읽을 수 있는 눈높이로 쓴다.
- **키워드 배치**: 메인 키워드를 제목(이미 포함)과 도입부 첫 2~3문장 안에 1회, 본문 중간에
  자연스럽게 1~2회 더 넣는다. 억지로 반복하지 않는다(키워드 스터핑은 검색 노출에 불리함).
- **구성**: 도입부(공감 가는 후킹) → 본문("OO가 뭔지" 쉬운 설명 + 관리법·실천 팁, 소제목
  활용 가능) → 마무리(요약 + 다음 글 예고나 구독 유도 한 문장) → 위 "지어내지 않기"에서 정한
  면책 문구 한 줄.
- **저장**: 마크다운 기호 없이 순수 텍스트로 저장한다 — 사장님이 그대로 복사해서 네이버 블로그
  에디터에 붙여넣을 수 있어야 한다.
- 초안은 참고용 뼈대이지 최종본이 아니다. 그대로 발행하지 말고 한 번 훑어보고 손봐서 올리도록
  안내한다.

## 완료 전 검증 (2026-11-18 추가)
초안이 "괜찮아 보인다"는 에이전트의 느낌은 검증이 아니다. 사장님께 보내기 전에, 실패할 수 있는
항목을 실제로 검사하고 근거와 함께 통과/실패를 남긴다. 검사는 두 종류다.

**1) 기계 검사 — `tools/draft_checker.py`가 한다.** 에이전트가 판정하지 않는다.
- 건강 전체: 주제 3개 / 키워드 3개가 서로 다름
- 건강 초안마다:
  - 필수 항목(title·keyword·search_intent·target_analysis·keyword_analysis·differentiation) 채움
  - 메인 키워드가 쇼핑·제품형이 아님 (추천·최저가·가격·구매 등)
  - 롱테일 후보가 있었다면 그 목록에서 골랐고, `keyword_analysis`에 실제 월간 검색량을 그대로 적음
  - 발행 글과 제목이 같지 않음. 같은 키워드의 발행 글이 있는데 `differentiation`에
    "관련 기존 글 없음"이라고 쓰면 실패 (그 글 제목과 다른 각도를 적어야 함)
  - `=== 본문 ===` 구분선 있음 / 분량 750~1300자(공백 포함, 줄바꿈 제외)
  - 메인 키워드가 제목에 있고, 도입부 3문장 안에 있고, 본문에 2~5회 나옴
  - 마크다운 기호(#, **, - 목록, >) 없음 / 끝부분에 면책 문구("정보 제공" + "병원") 있음
  - 금지 표현 없음: 완치, 100%, 무조건, 특효, 기적, 부작용 없음, 확실히/반드시 낫, 당신은, 틀림없
    (목록은 `tools/draft_checker.py`의 `BANNED_PHRASES`. 사장님이 추가하면 거기에 넣는다)
- 수술실 주제: 3개 / 필수 항목 채움 / 출처가 "체크리스트 2개 + 주제 축 1개" / 체크리스트 항목이
  ✅(이미 씀)가 아님 / 체크리스트 2개가 서로 다른 영역 / 주제 축이 오늘 `or_axes`에 있고 1·2번과
  겹치지 않음

**2) 근거 대조 — 에이전트가 하되, 근거를 반드시 적는다.**
- **숫자 근거**: 검사 도구가 "확인필요"로 뽑아준 숫자(%, mg, mmHg, 명 등)마다 근거를 댄다.
  대한의학회·질병관리청 기준처럼 공인된 진단 기준값이면 기준 이름을 적는다. 근거를 댈 수 없으면
  숫자를 지우고 정성적 표현("흔히", "많은 사람들이")으로 바꾼다 — "지어내지 않기" 원칙.
- **제목과 본문 일치 (어그로 방지)**: 제목이 약속한 것(질문·방법·비교)에 본문의 어느 문장이
  답하는지 초안마다 한 문장을 인용한다. 인용할 문장이 없으면 본문을 보강하거나 제목을 고친다.
- **진단형 단정·제품 추천**: 금지어 목록에 없는 표현이라도 "당신은 OO입니다"식 단정이나 특정
  약·제품을 권하는 문장이 없는지 다시 읽는다.

**실패했을 때**
1. 실패한 항목을 고치고 `draft_checker.py`를 다시 돌린다. 최대 2번까지 고친다.
2. 첫 검사에서 실패가 5개 이상이면 땜질하지 않는다. 어느 단계(키워드 선택·초안 작성·JSON 정리)가
   원인인지 보고에 적고, 그 단계부터 다시 한다.
3. 2번 고쳐도 남은 실패는 숨기지 않는다. 결과물은 보내되 보고에 "실패 남음: 무엇·왜"를 적는다.
4. 확인할 수 없는 항목은 통과로 치지 않는다. "확인필요 + 이유"로 보고한다.
5. 검사 도구가 잘못 판정했다고 판단되면(예: 정상인데 실패), 그 사실을 보고에 적고
   `workflows/notes.md`에 기록한다. 도구를 마음대로 느슨하게 고치지 않는다.

- 네이버 데이터랩/유튜브 API 호출이 실패하면: 마지막으로 성공했던 캐시 데이터로 대체하고,

- `report_builder.py` 실행(6번 단계) 자체가 에러로 실패하면(예: posts 필드 누락) 에러 내용을

  같은 문제가 자동으로 처리되게 한다.
- 결과물이 틀렸다는 지적을 받으면 채팅에서만 고치고 끝내지 않는다. 먼저 어느 쪽 문제였는지
  가린다: **절차**(단계가 빠졌거나 규칙이 문서에 없음) / **도구**(Tool이나 data 파일이 틀림) /
  **검증**(이 실수를 잡을 검사 항목이 없음). 그 자리에 가장 작은 수정을 하고,
  `workflows/notes.md` 맨 위에 날짜·무엇이 틀렸나·무엇을 바꿨나를 한 줄 남긴다. 같은 실수가
  두 번째면 부드러운 당부가 아니라 명시적 규칙이나 검사 항목으로 막는다.

  직접 해야 하는 영역이기 때문 (2026-08-09부터 이렇게 나뉨).
- `tools/draft_checker.py` — 완료 전 검증. report JSON·초안·발행 글 목록·업무 지식 체크리스트를
  대조해 항목별 통과/실패/확인필요를 출력하고 `_check.txt`로 저장한다. 실패가 있으면 종료 코드 1.
  네이버 검색 결과(display JSON)는 열지 않는다.
- `tools/report_builder.py` — 2단계. 에이전트가 posts를 채운 JSON을 받아 최종 PDF로 조립한다.
  `python tools/report_builder.py <json경로> <pdf경로>` (인자 없이 실행하면 샘플 데이터로 테스트
  가능). [[economy_daily_reports]]의 `economy_report_builder.py`와 같은 패턴.

## 알려진 한계 (사장님이 알아야 하는 것)
- 네이버 블로그의 실제 "인기 포스팅 순위"(조회수/좋아요)는 공식 API로 볼 수 없음. 지금은
  "검색 관심도가 얼마나 올랐는지"와 월간 검색량으로 대체하고 있음. 블로그 글 수는 약관상
  AI에 넣지 않고 PDF에만 표시하므로, 경쟁 판단은 사장님이 PDF 표를 보고 한다.
- 검색광고 API는 2026-11-01에 연동 코드를 넣었음. 키를 .env에 넣어야 실제로 작동한다.
  월간 검색량은 실제 수치지만, 광고 경쟁도(`competition`)는 광고 입찰 경쟁이지 블로그 경쟁이
  아니므로 참고만 한다.
- 유튜브 검색은 하루 호출 수를 최대 8회로 제한해뒀음(쿼터 절약). 카테고리 3개를 다루는
  지금은 하루 3회 호출됨.
- 카테고리 2개는 11개 카테고리를 날짜로 순서대로 도는 방식이라, 완전히 한 바퀴 도는 데
  대략 5~6일 걸린다. "오늘 상승률이 가장 높은 카테고리"를 놓칠 수 있다는 뜻이지만, 그 대신
  매일 다른 주제를 확실히 보장한다 — 사장님이 이 트레이드오프에 동의해서 채택한 방식.
- 검색의도·타겟·키워드 분석과 포스팅 초안은 에이전트가 그때그때 직접 쓰는 콘텐츠다. 데이터
  근거(상승률·경쟁도)는 실제 API 값이지만, 문장 자체는 참고용 초안이지 최종본이 아니다 —
  발행 전에 한 번 훑어보고 손보는 걸 권장한다 (의학적 사실관계는 특히).
